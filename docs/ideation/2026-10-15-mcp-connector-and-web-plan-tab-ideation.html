Top pick

Idea 1, giving every session on the Plan tab its reason and its result, answers the recurring "the Plan tab shows nothing" complaint with data that already exists. Idea 2 is the bigger bet: it makes the MCP connector obey the guardrails the product's own AI already obeys.

Grounding Context

Codebase Context

DA2 is an endurance and triathlon training app whose wedge is "AI periodization with coach review". apps/web hosts the UI, every API route, and the MCP endpoint; the Flutter app and the shared Zod package sit alongside. There is no STRATEGY.md.

  • MCP connector: one endpoint, /api/mcp, with a hand-rolled OAuth 2.1 server (open dynamic client registration, PKCE S256, 1h access and 30d refresh tokens). It exposes 16 tools: 8 reads and 8 writes over profile, completed and planned workouts, plans, and a CTL/ATL/TSB summary. Each call mints a 60-second Supabase JWT and an RLS-bound client. There is a single scope, athlete.
  • Not exposed over MCP: plan generation, plan archive and delete, weekly-review proposals and accept/reject, workout reports, period reviews, matched completion, coach links. No prompts, resources, elicitation, or MCP Apps are used.
  • Web Plan tab: rebuilt on 2026-10-14. PlanOverview derives week progress, volume bars, sport mix, next session and this week from planned workouts. The query selects only id, scheduled_date, sport, status, structure. Rationale, planned load and intensity appear only on the planned-workout detail page; match state and CTL/ATL/TSB appear only on the calendar and reports.
  • Plan actions: generate (only when no plan is active), archive, delete, and accept/reject AI weekly-review proposals. Plans are create-only. Generation failures show raw reason: codes.

Institutional learnings that bind these ideas

  • docs/solutions/screens-show-content-not-row-metadata.md — a screen shows what the entity contains; a tab must not just point at another tab.
  • docs/solutions/adaptive-plan-engine.md — the deterministic guardrail layer is authoritative and re-validates at apply time; version is the staleness token.
  • Memory: planned-structure-key-drift (three duration spellings, free-text intensity, written by ad-hoc writers), matching-uses-athlete-timezone (UTC mis-filed about 10% of one athlete's workouts), plan-generation-three-faults (generation only succeeded from 2026-08-19).

External context

Every fitness MCP found is community-built. The TrainingPeaks one has 84 tools, a read/write split, server-computed TSS, and in-place updates instead of delete-and-recreate. None ships prompts, resources or elicitation, and none exposes a "pending coach review" state. Competitor plan screens lean on planned-versus-actual compliance (Intervals.icu) and swappable workouts (TrainerRoad).

1.

Sessions that carry their why and their result

Axis 4 · Plan tab content and insightConfidence 80%Complexity Medium
Description
Turn the Plan tab from a schedule digest into the place an athlete finds out whether the plan is working. Each session row carries the rationale and intensity target the AI already wrote and, once matched, a deterministic verdict chip. Weekly bars become planned versus executed, with compliance bands and a denominator that counts only what is due to date, so skipped or moved sessions do not inflate it. A forecast line runs the existing training-load model forward over remaining planned load to project fitness, fatigue and form to the end of the plan block, and to event_date when the block reaches it.
Basis
  • direct: apps/web/app/(athlete)/plan/page.tsx:151 selects only id, scheduled_date, sport, status, structure; the scout found zero matches for rationale|planned_load|intensity|workout_matches|tsb|ctl in PlanOverview.tsx and plan-summary.ts.
  • direct: plan-summary.ts:74-78 counts a session done by status only (if (w.status === "completed")); delta.ts:40,46,51 already defines duration, load and intensity tolerances (10, 15, 8 percent) and computeExecutionDelta.
  • direct: load-series.ts:28,30 sets CTL_TAU_DAYS = 42 and ATL_TAU_DAYS = 7; calc.ts:98-103 has formVerdict(tsb); invariants.ts already holds the ramp cap, TSB floor and taper window.
  • external: Intervals.icu compliance bands and its forum thread on weekly planned versus completed (forum.intervals.icu), where adding completed work to the denominator was the complaint.
Rationale
The tab was just rebuilt to show content, but a plan page that never mentions what the athlete actually did, or why a session is there, still reads as a calendar. Every ingredient is one query away and the math is already deterministic and tested, so this reuses logic rather than inventing it. It also removes the "plan load disagrees with the dashboard" failure users report across tools, because the tab calls the same functions as reports.
Downsides
  • The verifier found that generation uses PLAN_HORIZON_WEEKS = 4 (apps/web/src/ai/generation/prompts/generate-plan.ts:50), so most plans never reach event_date. "Arrive fresh on race day" is only honest when the block covers the event; otherwise frame the forecast as end-of-block form.
  • Forecast quality depends on planned_load and structure.load, which are sparse and drifted in production; idea 4 is the fix.
  • Verdict chips need a batched or lighter path than the per-workout report context (about six queries each) to avoid N+1 on a plan page.
  • Mobile has its own copy of the summary logic (plan_summary.dart), so any new rows land twice unless the logic is shared.
2.

Claude proposes, the Plan tab disposes

Axis 2 · MCP surface beyond CRUD (crosses axis 5)Confidence 70%Complexity High
Description
Today the connector's write tools edit rows directly, which means an assistant can schedule a load spike inside the taper window that the app's own AI planner would have dropped. Route plan-shaping writes (multi-day moves, load increases, anything near the event, anything on a coach-edited row) through the existing proposal pipeline: the tool compiles to the engine's five operation kinds, runs the deterministic validator as a dry run, and files a proposal the athlete accepts or rejects per operation in the Plan tab's existing review screen. Add read and decide tools so the assistant can say "you have a pending review". The read side is separable and can ship first.
Basis
  • direct: apps/web/app/api/weekly-review/route.ts:11-15: "Agent-native: … an agent can GET the list, then drive accept/reject on a specific [id]"; accept/route.ts:13-18: "re-validate invariants against CURRENT load … atomically apply via the apply_weekly_review RPC".
  • direct: packages/shared/src/edit-op.ts:67 defines move, modify, skip, insert and delete; apps/web/src/training-load/invariants.ts:1-24 documents validateOps as a pure function, with drop reasons volume_ramp, ctl_ramp, tsb_floor, taper_window, past_event, coach_protected.
  • direct: nothing under apps/web/src/mcp/ references validateOps or the entitlement gate, and the surface scout found no MCP tool that maps to generate, archive, delete, accept, reject, report or review.
  • external: no competitor exposes a "pending coach review" state to an assistant; Humango and Runna adapt silently. The pattern mirrors suggestion mode in document editors and pull requests in code review.
Rationale
It is the only way an external assistant and the in-app AI coach can both edit one plan without overwriting each other or bypassing the safety layer the product sells. It also turns the Plan tab into the approval surface for what Claude wants to do, which gives the tab a reason to exist beyond display.
Downsides
  • The verifier found real conflicts: propose_weekly_review is service-role only while the connector is deliberately JWT-only; the trigger_kind check has no agent value, so a migration is needed; and the single-open-proposal precedence logic could let an agent proposal supersede, or be suppressed by, the weekly AI review.
  • Accept is gated on the ai_plans entitlement, so non-subscribers' MCP edits would newly be gated. Decide that deliberately.
  • Proposals only render on /plan when an active plan exists.
  • Slice it: pending-review reads plus accept and reject are small to medium; proposal authoring is the large part.
3.

A provenance spine: audit every agent write, show it, undo it

Axis 1 · Agent write safety (crosses axis 5)Confidence 75%Complexity Medium
Description
Put an actor claim and client id in the short-lived JWT the connector already mints, and let a database trigger write the audit row in the same transaction as the mutation, for planned workouts, completed workouts and profile alike. Store before and after values so an edit can be reversed. On the Plan tab, show "Changes since you last looked" with provenance (you, AI coach, coach, Claude) and an Undo that replays the inverse under the version guard.
Basis
  • direct: apps/web/src/mcp/tools.ts:5-7 promises "writes stamp agent attribution and append a workout_edits audit row", but appendAgentEdit is called only at lines 460, 512, 555 and 596 (planned writes). profile_update and the completed-workout log, edit and delete never call it.
  • direct: tools.ts:70-73: "The mutation already landed; never silently drop a failed audit append", so today the audit is a best-effort insert after the write; the minted JWT payload at crypto.ts:50-57 has no actor claim.
  • direct: supabase/migrations/0019_weekly_reviews_and_workout_edits.sql:119 makes planned_workout_id the only workout foreign key; packages/shared/src/realtime-allowlist.ts:30 already lists workout_edits, so live updates are possible.
  • external: aviation flight recorders and git reflog as the model for cheap, trustworthy reversal.
Rationale
The code comment currently claims an audit trail that does not exist for completed workouts, so an assistant can delete or alter real training history with no record. Letting an agent write to a plan is only comfortable if the athlete can see and reverse what it did. A trigger makes that structurally impossible to forget when tool number 17 is added.
Downsides
  • The verifier checked and found MCP rows store field_diff as {created:true}, {edited:[keys]}, {moved_to} or {deleted:true}, with no old values. Undo is impossible until the audit stores before and after; that is a core part of this idea, not an extra.
  • Auditing completed workouts and profile needs a migration or a sibling table, with account-deletion cascade handling.
  • "Since you last looked" needs per-user state. A cheap first slice is a badge from edited_by_kind = 'agent' on the planned rows, which needs none of the above.
  • docs/operational/mcp-connector.md also names the wrong audit column (edited_by_kind where the code uses actor_role).
4.

One canonical write gate for planned workouts

Axis 1 · Agent write safety and data integrityConfidence 85%Complexity Medium
Description
Stop accepting an open structure blob on MCP planned-workout create and edit. The assistant supplies intent (sport, date, duration, an intensity target, or a compact step list); the server builds the canonical stored shape, computes planned_load, normalizes legacy keys on edit, and rejects anything else with a specific, model-readable error such as "use duration_s, not est_duration_min". Put this behind one write function shared by MCP, REST, coach routes and the AI generator.
Basis
  • direct: apps/web/src/mcp/tools.ts:424,478 are structure: z.record(z.unknown()).optional() and :449 stores args.structure ?? {}.
  • direct: apps/web/src/ai/planned-structure.ts:39-41: "a survey of live rows found THREE spellings in use, each from a different writer"; lines 53-54 say "the durable fix is for generation to settle on one key".
  • direct: a strict canonical schema already exists at packages/shared/src/plan-generation.ts:117-126 (GeneratedWorkoutStructureSchema … .strict()).
  • external: the TrainingPeaks MCP computes TSS and intensity factor server-side from the interval structure (JamsusMaximus/trainingpeaks-mcp).
Rationale
The connector is the newest ad-hoc writer, and the key-drift learning says drift comes from exactly such writers. A language model will happily invent a fourth duration spelling, and the Plan tab's weekly bars then show a silent zero for that row. This is also the foundation that ideas 1 and 7 quietly depend on.
Downsides
  • Existing rows still need a legacy read and normalize path; this closes the door but does not clean the room.
  • planned_load is optional on MCP create today, so the server must start deriving it.
  • The strict generation schema requires a phase field the connector may not want to demand.
  • Prod JSONB should be measured before fixing the canonical shape, per the drift learning.
5.

Hand Claude the app's own numbers, in the athlete's time

Axis 2 · MCP surface beyond CRUD (includes axis 3 timezone)Confidence 80%Complexity Medium
Description
Expose what the app already computes deterministically instead of raw rows: the per-workout execution verdict and deltas, period-review facts, the full CTL/ATL/TSB series with its form verdict, and a single "athlete brief" tool or resource. Ship a weekly check-in prompt that chains them. In the same change, resolve every date in users.timezone, return an athlete_today and week_start header, and accept today, this_week and next_week as date arguments.
Basis
  • direct: the workout report GET route states it will "NEVER call the LLM"; reviews/route.ts:1-10 says the same; the headline is templated by our code, "never model-written" (verifier located the quote at delta.ts:334 and the shared workout-report.ts).
  • direct: training_load_summary returns only the last 14 points via slice(-14) and no form verdict; the surface scout found zero registerPrompt or registerResource calls.
  • direct: apps/web/src/mcp/tools.ts:116-117 filters with `${args.to}T23:59:59Z` and :245-246 uses Date.now() - days * 86_400_000; tools.ts never mentions a timezone, against the AGENTS.md rule to apply athlete timezone at the read boundary.
  • external: stale cached CTL, timezone bugs that mis-date a race day, and plan load that disagrees with the dashboard are recurring pains across fitness MCPs and coaching tools (Intervals.icu IntervalCoach forum thread).
Rationale
An assistant that recomputes training load itself will eventually quote a number the app does not, which is the failure athletes notice first. The expensive, correct logic already exists and costs no model call. Fixing dates once at the boundary removes the bug class the project already paid for in matching, and the timezone slice is small enough to ship first.
Downsides
  • Whether claude.ai surfaces connector prompts is unverified, so treat prompts as an experiment and make the tools carry the value.
  • The report route gathers context per workout, so period-level facts need a batch variant.
  • The verifier noted many users may still hold UTC in users.timezone; check capture coverage first. It also flagged, unverified, that short training_load_summary windows may start CTL from zero.
  • Overlaps idea 1: both should call one shared plan-and-load read model rather than growing separate derivations.
6.

A connected-assistants panel with read-only consent

Axis 3 · MCP trust, auth and opsConfidence 80%Complexity Medium
Description
Add Settings, Connected assistants: each client with its name, connected date, last used, and write count, with Revoke and Revoke all. Wire up revokeAllForUser, which nothing calls today. Split the single athlete scope into read and write, let the consent screen offer "Approve read-only", and mark dynamically registered client names as unverified. Per-token write budgets and rate limits on /token, /authorize and tool calls are the second slice.
Basis
  • direct: docs/operational/mcp-connector.md:51-55 tells users to revoke with raw SQL, delete from oauth_access_tokens where user_id = auth.uid();; revokeAllForUser (apps/web/src/oauth/tokens.ts:172) has no caller.
  • direct: scopes_supported: ["athlete"] at .well-known/oauth-authorization-server/route.ts:23; the consent text at authorize/route.ts:78-80 says the client "wants to read and write your training data", and :154 shows a registrant-supplied client_name.
  • direct: supabase/migrations/0025_mcp_oauth.sql:129-134 gives athletes a self-SELECT policy only; the trust scout found no rate limit on token, authorize or tool calls (only registration, 5 per IP per hour), and 30-day refresh tokens.
  • external: Open Banking consent dashboards that let a person list and revoke third-party access; Claude's own per-tool permissions (always allow, needs approval, blocked) make read and write grouping matter.
Rationale
Open client registration plus a write-capable 30-day token and no way to see or kill it is the weakest trust point of the connector. A read-only tier is also the safest way for a cautious athlete to try it. This is the gate that lets ideas 2 and 5 expose riskier tools behind distinct scopes.
Downsides
  • The verifier called the full bundle oversized (UI, scope split, budgets, rate limits are four ideas). Ship the list plus revoke first.
  • Claude already offers client-side per-tool permissions, which lowers the value of the scope split for Claude, though not for other clients.
  • A "writes per client" count depends on idea 3 carrying a client id.
  • Revoke needs an admin-client route because only a self-SELECT policy exists.
7.

Plan generation you can preview and understand

Axis 5 · Plan tab actions and lifecycleConfidence 60%Complexity Medium (High for the preview half)
Description
Two separable moves. First, make failures actionable: an infeasible request returns "this event by this date needs at least N hours a week" with a one-click adjusted retry, status arrives by realtime instead of a 4-second poll, and the raw reason: codes leave the athlete UI. Second, build the new plan as a candidate beside the live one, show a diff (weekly volume, peak CTL, form at the end of the block, changed days), and promote it in one transaction only on confirmation; discarding costs nothing.
Basis
  • direct: supabase/migrations/0024_…sql:148-156 archives the active plan and soft-deletes its not-yet-done workouts inside create_ai_plan; lines 92-99 return trial_exhausted when the single free plan was already used.
  • direct: GeneratePlanCard.tsx:292 renders reason: {code} while :236-239 already holds the right advice ("try more weekly hours or a later event date"); POLL_INTERVAL_MS = 4_000; ai_generation_attempts is not on the realtime allowlist.
  • direct: PlanActions.tsx:108-118 warns that upcoming workouts will be removed from the calendar.
  • reasoned: generation only began succeeding on 2026-08-19 and each run costs about 7k of an 8k tokens-per-minute budget, so a result the athlete cannot compare or undo is a high-stakes action on an unproven output. Staged deploys with instant rollback are the standard answer.
Rationale
Generation is expensive, fragile and previously failed silently. Today the failure path shows internal codes with no remedy, and a successful run replaces the current plan unseen. Making the first half clear is cheap and independent; the second half makes regenerating safe to try, and is the point where the free-trial rule becomes a deliberate product decision.
Downsides
  • The verifier called this two ideas. Actionable failures and realtime status are small to medium and independent; candidate-and-promote is large.
  • The one-active-plan partial unique index and the rule that calendar and adaptive reads scope by athlete and deleted_at mean candidate workouts cannot simply be planned_workouts rows; they need a separate table or status.
  • "Discard is free" changes the trial semantics inside the RPC.
  • Lowest confidence of the set because the preview half has the least precedent in this codebase.

Rejection Summary

#IdeaReason rejected
1Prompt-injection taint tracking on MCP readsBasis weakened. The connector builds a new server and transport per request, so "sessions that have read foreign text" cannot be tracked, and the elicitation hand-off needs SSE, which is disabled. The cited generation-prompt precedent runs in the opposite direction. A usable slice (origin labels in tool output) is small enough to fold into idea 2.
2Golden-athlete parity test harnessSound but an enabler, not a direction. It should land first as a sequencing step before ideas 3, 4 and 5; only two MCP test files exist and no tools.ts test.
3One plan read model for web, mobile and MCPA refactor with no user-visible change; the "select string copied three times" point is a trivial dedupe. Folded into ideas 1 and 5 as an implementation note.
4"Life happened" actions (travel, injury, race date moved)Premise does not hold. The replan request carries only a trigger kind and optional workout id, and the route header says no endpoint for availability or event-date changes exists and should not be invented. Revisit once such an endpoint is built.
5Plan tab rendered inside Claude as an MCP AppUnverified platform support: the closest prior art says its MCP Apps did not render in Claude clients as of July 2026, contradicting the host-support claim. Needs a render spike, and a data contract from ideas 1 and 5 first.
6Bring-your-own-model plan generation (plan_context / plan_submit)Sound, but a strategy change: it hands the core wedge to the user's assistant, labels the result ai_generated, and changes entitlement economics. Better handled as a brainstorm variant than a product improvement.
7Merged away: separate undo ledger, separate planned-versus-actual card, separate forecast, separate timezone contract, separate three-way "agent edits as proposals" cardsDuplicates of stronger ideas. The undo ledger's original premise (old values exist) was refuted, so its requirement moved into idea 3; the others folded into ideas 1, 2 and 5.
