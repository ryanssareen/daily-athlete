## Failures

### Activity dates off by one day (UTC vs athlete timezone) · Athlete
- Observed: the same completed workout (`911ed6ac-a15c-4b4a-b044-97e7a530a7e5`, "KeyBike_7Aug.mrc") showed **Sep 7** on the calendar and on its own detail page (`Sep 7 · 4:55 AM`), but **Sep 6** on `/athlete/activities`. Confirmed via `read_page` text (not just visually) on both pages, ruling out a rendering artifact.
- Status/body: not a failed request — no error, no bad status. A silent display bug: the correct date was fetched, just formatted wrong.
- Root cause (confirmed, read from source): `apps/web/app/(athlete)/athlete/activities/page.tsx`'s `fmtDay`/`fmtYear` hardcoded `timeZone: "UTC"` / `getUTCFullYear()` instead of using the athlete's timezone. For an athlete at UTC+5:30, a 4:55 AM local start falls on the *previous* UTC calendar day. Every other date-rendering path in the app (`formatWorkoutDateTime`, `calendarDayInTimezone` in `src/lib/format.ts`) already threads `session.timezone` through for exactly this reason — this page was the one place that didn't.
- Fix: threaded `session.timezone` (already available from `getUserWithRoles()`, no new fetch needed) into `fmtDay`/`fmtYear`. Commit [`4b4f558`](https://github.com/ryanssareen/daily-athlete/commit/4b4f5586d02debe48c15be312f08c3962afe0c37). Re-verified live against production after deploy: the same workout now shows **Sep 7** in both places.

### Raw markdown in planned-workout rationale text · Athlete
- Observed: `/athlete/planned/[id]` → "Why this workout" rendered `**Home strength circuit, approx 25min.**` literally (with asterisks), not as bold, and the bullet-list/paragraph structure ran together on one line.
- Status/body: not a failed request — a silent display bug, same class as the date issue above.
- Root cause (confirmed, read the actual prod row via `supabase db query --linked` against the `planned_workouts.rationale` column for this exact workout): the stored text genuinely contains `**bold**` spans and `\n\n`-separated paragraphs/bullets (the model treats this field as loosely-markdown, unlike the report-narration prompts which explicitly say "no markdown"). The page rendered it in a plain `<p>` with default `white-space` and no markdown handling at all, so the newlines collapsed and the `**` markers showed up as literal characters.
- Fix: added `parseRationaleRuns()` (pure function, 5 new unit tests) that splits only on `**bold**` into plain-text runs rendered as `<strong>`/text nodes — no HTML interpretation, keeping the file's existing R7 contract ("plain text only, never `dangerouslySetInnerHTML`", already covered by an existing regression test). Paired with `white-space: pre-wrap` on the paragraph so the model's blank-line/bullet structure survives. Commit [`dec93a7`](https://github.com/ryanssareen/daily-athlete/commit/dec93a7811ec07108b3b6c5c6e793ba692751850).
- Re-verify: confirmed live — the bold lead-in now renders as a separate `<strong>` node (verified via `read_page`, not a screenshot) instead of literal `**` characters. The `pre-wrap` line-break behavior is in the shipped code and unit-tested, but couldn't be independently visually re-confirmed through `read_page` alone (accessible-name computation collapses whitespace by spec regardless of the actual rendered layout) — noting this as inferred-from-code-and-tests, not directly observed, per the "verified vs. inferred" distinction.
